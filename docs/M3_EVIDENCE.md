## Wave 1 — classpath & JAR loading (T08–T11)

**Delivered.**

1. **Zero-dependency archive reader** (`j2r-classfile`):
   - `crc32.rs` — table-driven CRC-32 (RFC 1952), 2 unit tests (known
     vectors incl. `123456789 → 0xCBF43926`; streaming == one-shot over
     10 000 bytes).
   - `inflate.rs` — RFC 1951 DEFLATE decoder, iterative bit-at-a-time
     canonical-Huffman walk (puff-style; no recursion, so a hostile
     stream cannot overflow the native stack). 11 unit tests: stored
     blocks (single + multi), LEN/NLEN mismatch, truncation, reserved
     block type, empty input, bomb guard (40 000 B block vs 20 000 B
     cap), and **real-JDK vectors** — raw `Deflater` streams at levels
     0/1/9 over a 7 681-byte payload (committed under
     `crates/j2r-classfile/tests/vectors/`, generated by Temurin
     21.0.13, provenance in `tests/vectors/README.md`) plus trailing-
     garbage tolerance. The fixed distance table (30 of 32 five-bit
     codes) and incomplete dynamic distance tables decode per RFC 1951
     §3.2.6/§3.2.7; invalid codes demanded at decode time are loud
     errors.
   - `zip.rs` — EOCD backward scan with comment-length validation,
     central-directory parse, ZIP64 loudly rejected, STORED + DEFLATED
     entries, local-header name sanity check, per-entry CRC-32
     verification, encrypted-entry rejection, 64 MiB inflate cap.
     8 unit tests incl. hand-built archives and the JDK-produced
     `jdk_l9.zip` round-trip.
2. **Classpath resolution + transitive closure** (`j2r-codegen`):
   `classpath.rs` — ordered dirs + `.jar`/`.zip` (first-match-wins),
   archives parsed once at construction, closure loader walks every
   `CONSTANT_Class` reference of every loaded class (`ClassFile::
   referenced_classes`, array descriptors decoded), JDK namespaces never
   loaded from the classpath. `compile()` accepts empty inputs +
   `--main-class` to seed the walk; a missing referenced class is a
   compile error naming the referer. 2 unit tests (array-decode table,
   JDK-namespace predicate incl. the `javafx` prefix trap).
3. **CLI**: `-p/--classpath` on `compile` and `build`
   (`value_delimiter = ':'`, dirs/jars/zips), classpath-only compiles
   with `--main-class`.
4. **Jar differential harness** (`crates/j2r-cli/tests/jar_suite.rs`,
   3 tests):
   - `jar_differential_suite` — 4 fixtures under `tests/suite_jar/`
     (39 + 4 = 43 fixture programs total in the repo):
     `JarMain` (3 classes/2 packages, cross-package static-init order,
     cross-class virtual dispatch), `JarSuper` (abstract superclass +
     interface in a jar, override dispatch, array of abstract type),
     `JarDup` (same class in a classpath dir and in the jar; both JVMs
     must pick the dir copy), `JarClosure` (30-class chain, only C1
     named; eager field-initializer construction pulls the whole chain
     through the closure). Each fixture: `javac` → real `jar` tool →
     `j2r compile -p app.jar --main-class …` (no inputs) → `cargo
     build` → three-channel compare vs `java -cp app.jar …`.
   - `jar_vs_exploded_determinism` — compiling the same program from
     the jar and from the exploded classes dir produces byte-identical
     generated sources (M3_PLAN §4.6 determinism guard).
   - `missing_class_fails_loudly` — a referenced-but-absent class fails
     compilation and the error names the referer.

**Defects the new fixtures caught** (both fixed, both pinned by the
suite — the fixture suite exists to catch exactly this class of bug):

1. *Classpath dir entries read the wrong path* — `Classpath::read` used
   the bare relative entry name instead of `dir.join(rel)`. Found by
   `JarDup` ("cannot read Dup.class"); the dup fixture now permanently
   exercises the dir-vs-archive precedence path.
2. *Interface-inherited virtual calls rejected* — `validate_virtual`
   walked only the superclass chain; JVMS 5.4.3.3 resolves
   `invokevirtual` through superinterfaces, and javac emits the
   receiver's compile-time type as owner even when the method is
   declared in an implemented interface. Found by `JarSuper`
   (`shapes[i].area()` where the static type is the abstract class
   `Shape` and `area()` is declared on the interface `Area`). Fixed by
   making validation a graph walk over `super_name` + `interfaces`
   (deduplicated), continuing into builtin ancestors. The runtime
   dispatch walk already covered interfaces (generated `parents_of`
   includes them) — the gap was validation-only, so the fix widens
   acceptance and cannot reject previously-valid programs.

**Honesty notes.**

- The closure is over-approximate: it loads every class *named* in a
  `CONSTANT_Class` entry, not only the ones actually executed — the
  ahead-of-time whole-program model requires the complete closure at
  compile time (JVM behavior defers the error to first active use; we
  fail at compile time, same trade-off as the M1 reference universe,
  documented in M3_PLAN §4.2).
- Archives: STORED + DEFLATED only; ZIP64, multi-disk, encrypted
  entries, and non-`.class` resource APIs are loud errors or ignored
  (documented in M3_PLAN §4.2); the 64 MiB per-entry inflate cap is a
  compile-time limit mirroring the M2 SOE-ceiling philosophy.
- `Jar<'static>` uses `Box::leak` for the archive bytes (one archive
  set per compiler invocation, compile-time only) — noted here and in
  the source because it looks alarming out of context.

**Test inventory at wave end (local, Temurin 21.0.13, release):**
196 tests, 0 failures — 26 classfile (5 pre-existing parser + 21 new
archive/reader), 10 cli unit, 59+4 codegen unit+integration, the
39-fixture three-channel differential suite, the 3-test jar suite above,
the SOE boundary e2e, the forced-GC suite, and the 39-fixture
`--emit-cfg` equivalence run.

**Acceptance criteria (M3_PLAN §4.7):** all three checked —
classpath-only compile + runnable crate for all four jar fixtures
(three-channel green); inflate battery green with no panic on any
corrupted input tested; suite guards raised (diff suite `>= 39` kept,
jar suite `>= 4`); CI gates green at the wave commit (run recorded in
ROADMAP §2).

## Wave 2 — java.util collections & java.lang extensions (T12–T15)

**Delivered.**

1. **`crates/j2r-runtime/src/collections.rs` (new, ~1 750 lines incl. 18
   unit tests)** — `ArrayList`, `HashMap`, `HashSet`, their iterators and
   views, and `Objects`, all **heap-resident** (M3_PLAN §5.4): every
   collection is a `JObj` whose slots hold scalars and references to
   backing `[Ljava/lang/Object;` / `[Ljava/util/HashMap$Node;` arrays, so
   the M2 mark/sweep scans collections with **zero new root machinery**.
   Slot layouts are documented in the module header; `builtin.rs` owns the
   same numbers as the single source of truth for `new_builtin`.
2. **HashMap is algorithm-faithful to OpenJDK** (risk M3-R2):
   `h ^ (h >>> 16)` spreading (logical shift — a bug where Rust's
   arithmetic `>>` leaked in was caught by a hand-pinned unit test),
   `tableSizeFor` including the `cap <= 1 -> 1` underflow edge, lazy table
   allocation (initial-capacity ctor stores the rounded capacity in
   `threshold` exactly like JDK 8), load factor 0.75 with **float**
   arithmetic for the threshold recompute, doubling resize with the
   Java-8 lo/hi bin split **preserving relative order** (the missing
   `loTail.next = null; hiTail.next = null` terminator was caught by the
   `hashmap_order` unit test — a node iterated from two bins), tail
   insertion within bins, table-order iteration. The `HashMapOrder`
   differential fixture prints byte-identical iteration order vs Temurin
   21 across a 13th-put resize, `Integer`/`String` (deliberate `Aa`/`BB`
   hash collisions)/user-class keys (dispatched `hashCode`/`equals`), and
   the `MapBoxKeys` fixture extends this to `Long`/`Double`/`Character`
   keys.
3. **`ConcurrentModificationException` is modelled** (M3_PLAN §5.3
   decision): `modCount` lives in a collection slot; iterators capture it
   and `next()` checks it *first* (CME before `NoSuchElementException`,
   exact OpenJDK order); `hasNext()` does **not** check, matching
   `HashIterator`/`Itr` semantics — both pinned by unit tests and the
   `ArrayListOps`/`HashMapOrder` fixtures. Replace-put is not a structural
   modification (no CME) — unit-tested.
4. **`ArrayList$Itr.remove()` is Java-faithful — recorded plan deviation**:
   M3_PLAN §5.2 drafted `Iterator.remove()` as a loud unsupported runtime
   error. The `ArrayListOps` fixture caught the difference: Temurin's
   `ArrayList$Itr.remove()` works, removes the last-returned element,
   rewinds the cursor and re-syncs `expectedModCount`. Faithful >
   convenient: the implementation now mirrors `Itr.remove()` (incl.
   `IllegalStateException` with a null message when no `next()` preceded),
   the differential fixture pins it, and this note is the disclosure.
   `HashMap` iterators' `remove()` remains a loud
   `UnsupportedOperationException("remove")` (unexercised by fixtures,
   outside the §5.2 inventory — still no third state: it fails loudly at
   runtime rather than silently misbehaving).
5. **`java.lang` extensions** (`langext.rs`, new): `String`
   (`substring`/`indexOf`/`lastIndexOf`/`concat`/`replace`/case mapping/
   `trim` with Java's `<= U+0020` semantics/UTF-16 `compareTo`/
   `compareToIgnoreCase`/`startsWith`/`endsWith`/`contains`/
   `equalsIgnoreCase`/`toCharArray`/`repeat`), `StringBuilder`
   (`reverse`/`insert` ×4/`deleteCharAt`/`delete`/`replace`/`setLength`/
   `capacity`/`charAt`/`indexOf`/`(I)V` ctor), `Math`
   (`floorDiv`/`floorMod` ×2, `round` ×2, `sqrt`, `cbrt`, `pow`, `floor`,
   `ceil`, `signum` ×2, `toIntExact`, `addExact`/`subtractExact`/
   `multiplyExact` ×3 widths incl. the `(long,int)` overloads javac picks
   for mixed-arity call sites), `Integer`/`Long` (unsigned radix
   formatting, `compare`, `max`/`min`/`sum`, `bitCount`,
   `numberOf{Leading,Trailing}Zeros`, `{highest,lowest}OneBit`,
   `rotate{Left,Right}`, `reverse`, `parseInt(String,int)`), `Character`
   (classification per the JDK definitions incl. Java's `isWhitespace`
   set — which differs from Unicode `White_Space` — and Nd digit ranges),
   plus `Objects.equals/hashCode/requireNonNull ×3/toString/isNull/
   nonNull`.
6. **Java-exact message texts, three-channel pinned** — every message was
   captured from Temurin 21 first and matched, several differ from
   intuition or older JDKs: `substring` bounds are
   `Range [5, 2) out of bounds for length 12` (JDK 21
   `checkBoundsOffCount` shape), `ArrayList.get` is
   `Index 5 out of bounds for length 3` but `add(int,E)` is
   `Index: 5, Size: 3`, `StringBuilder.charAt/deleteCharAt` are
   `Index i out of bounds for length L` while `insert/delete/replace` are
   `Range [s, e) out of bounds for length L`, `new StringBuilder(-1)`
   throws **`NegativeArraySizeException("-1")`** (not
   `IllegalArgumentException` — COMPACT_STRINGS `new byte[cap]`), radix
   `parseInt` failures append ` under radix R`, `Math.toIntExact` and the
   exact family use `integer overflow` / `long overflow`, `String.repeat`
   uses `count is negative: N`, `ArrayList(-5)` uses
   `Illegal Capacity: -5`, `HashMap(-3)` uses
   `Illegal initial capacity: -3`, and `Integer.parseInt(null)` uses
   `Cannot parse null string`.
7. **`String.toString()` registered** (returns `this`) — the census of
   existing entries showed it missing, so dispatched `toString()` on a
   String element previously fell through to `Object.toString`; caught by
   the first `ArrayListOps` run, fixed before any commit.
8. **Borrow census re-issued** (`RUNTIME_SAFETY.md §4`): zero direct
   object borrows in the new files; **0 of the 68 accessor closures in
   `collections.rs` + 4 in `langext.rs` contain `invoke_virtual`**
   (script-verified) — dispatch helpers read first, then dispatch with no
   heap borrow held.

**Test inventory at wave end (local, Temurin 21.0.13):** 18 new
`collections.rs` unit tests (tableSizeFor edges, hash spreading with
hand-pinned values incl. negative hashes, ArrayList ops/bounds/CME/
exhaustion/`Itr.remove`/`IllegalStateException`, HashMap order with
collisions + resize, replace-vs-structural CME semantics, views, null
key/value, iterator CME, HashSet, Objects overloads, and the two GC
integration tests: a rooted collection keeps elements alive across 50
forced collections and a dropped collection is collectable whole), all 12
new fixtures (51 total) three-channel green, and the five collection
fixtures re-run under `J2R_GC_EVERY_N=1` forced collection at every
allocation point — byte-identical output.

**Acceptance criteria (M3_PLAN §5.6):** every §5.2 method either works
differentially or fails loudly at compile time (the natives table is the
compile-time gate — unregistered = resolve error);
`HashMapOrder` prints byte-identical iteration order vs Temurin incl. the
post-resize order; forced-GC run green over the collection fixtures (gate
9 runs the full suite under `J2R_GC_EVERY_N=1` in CI); borrow census
re-issued in `RUNTIME_SAFETY.md` §4 in the wave commit. Suite guard raised
to `>= 51`.

## Wave 3 — lambdas & method references (T16–T18)

**Delivered.**

1. **Bootstrap-argument resolution** (`j2r-classfile`):
   `BootstrapArgument` gains `MethodType(String)`, `MethodHandle
   { kind, class, name, desc }` and `Class(String)` — resolved at parse
   time instead of the old `Opaque { tag }` (which is kept for genuinely
   exotic constants). `makeConcatWithConstants` rejection text for
   MethodType/MethodHandle/Class constants is unchanged in behavior.
2. **Compile-time site resolution** (`j2r-codegen/src/lambda.rs`, new):
   `bootstrap_class_of` dispatches each indy site on its bootstrap class —
   `LambdaMetafactory.metafactory` → `resolve_lambda`,
   `StringConcatFactory` → the unchanged `resolve_concat`, anything else
   → `unsupported invokedynamic bootstrap {cls}`. `resolve_lambda` pins,
   with loud errors naming the shape:
   - the functional interface must be in the M3 nine-interface set
     (`IntPredicate`, `ToIntFunction`, … → "outside the M3
     LambdaMetafactory set" — negative e2e `lambda_neg.rs`);
   - the bootstrap handle must be exactly `LambdaMetafactory.metafactory`
     (`altMetafactory` → loud, covered by the same dispatch check);
   - `samMethodType` arity must equal the interface's SAM arity,
     `instantiatedMethodType` must agree, and the erased SAM return kind
     is pinned per interface (`Object` for the Function family, `V` for
     consumers, `Z` for predicates);
   - `implMethod` kinds 5/6/7/8/9 with per-shape arity rules: static
     `impl == caps + sam_arity`; bound (captures>0) `impl == sam_arity`;
     unbound (captures==0) `impl == sam_arity - 1` (the receiver arrives
     as the first SAM argument — `String::toUpperCase` is impl
     `()String` against SAM `apply(Object)Object`); special requires a
     captured receiver; ctor references must return void and resolve to
     an instantiable class (compiled `total_slots` or
     `builtin_total_slots`);
   - the target must resolve (compiled classfile member or natives row)
     — a broken closure can no more reach runtime than a broken call.
   The plan carries shape (`0 static / 1 bound / 2 unbound / 3 ctor`),
   interface, SAM name, capture kinds and target; `ClassPlan.lambdas`
   mirrors `concats`; the verifier pops capture kinds and pushes `Ref`
   for lambda sites (arity/type simulation unchanged); the
   `validate_indy` pre-check accepts either map.
3. **Closure construction** (emission): every indy lambda site emits
   `lambda::make_closure(shape, iface, target_class, target_name,
   target_desc, ctor_slots, &captures)` after the standard call-boundary
   root refresh — captures are rooted through the frame snapshot exactly
   like call arguments (M2_PLAN §4.4 discipline).
4. **Runtime invocation** (`j2r-runtime/src/lambda.rs`, new): a closure
   is an ordinary heap object **whose class is the functional interface
   itself** — subtype checks and `invokeinterface` dispatch are exact
   through the existing machinery with zero new root or dispatch code
   (slots: shape, target class/method/desc, ctor slot count, captures).
   `n_sam` (one natives row per interface) reassembles the call and
   performs the adaptation `LambdaMetafactory` would do at link time:
   boxed SAM arguments are unboxed to primitive impl parameters, and
   primitive impl results are boxed back to the erased `Object` SAM
   return (verified live against javac 21 output — `square:(I)I` is
   emitted raw). Null receivers → NPE, matching invocation on null.
5. **Interface-dispatch wiring**: builtin hierarchy for the nine
   interfaces (`UnaryOperator <: Function`,
   `BinaryOperator <: BiFunction` via the interface table); SAM rows for
   all nine; Wave-2's loud `Supplier.get` placeholder became the real
   `lambda::n_sam` row (first match wins in the table — the duplicate
   was caught by the first differential run); `ArrayList.forEach/removeIf`
   registered under both `java/util/ArrayList` and `java/util/List`
   (the Wave-2 mirror-row pattern), with OpenJDK-faithful semantics:
   `forEach` checks `modCount` after every element, `removeIf` computes
   the removal set in one pass (CME if the predicate structurally
   modified the list) then compacts once with a single `modCount`
   increment.
6. **Name mangler fix**: `$` is legal in JVM method names (javac's
   synthetic `lambda$main$0`) but not in Rust identifiers —
   `method_fn_name` now escapes it (`_d_`), and the first run caught the
   generated crate failing to compile without it. Documented limitation:
   the escape is not injective against an adversarially hand-written
   class declaring both `lambda$main$0` and `lambda_d_main` with the
   same descriptor (javac output can never do this; a crafted classfile
   fails loudly with a duplicate-symbol compile error in the generated
   crate, never a miscompile).

**Honesty notes (per M3_PLAN §6.1 decisions).**
- Closure `getClass()` reports the functional interface, not a synthetic
  `$$Lambda$…` name — fixtures never print lambda class names (Temurin's
  names are JVM-specific).
- `andThen`/`compose`/`negate` default methods are loud-unsupported
  (unknown-JDK-method compile error), per the plan's no-default-methods
  decision.
- Lambda markers via `altMetafactory` (`FLAG_SERIALIZATION`) are loud.
- A closure built for one interface fails `instanceof` for the other
  eight (correct: the object class *is* the interface) — exactly
  Temurin's semantics.

**Tests.**
- `lambda.rs` (codegen) unit tests: SAM arities for all nine interfaces,
  SAM return-kind pinning incl. the three rejection classes, capture-kind
  alphabet.
- `lambda_neg.rs` (j2r-cli, javac-gated): `IntPredicate` and
  `ToIntFunction` lambdas are rejected at compile time with the
  set-membership message.
- Nine differential fixtures (suite 51 → 60, all three-channel green vs
  Temurin 21.0.13):
  `LambdaCaptureless` (all nine interfaces, no captures),
  `LambdaCapture` (reference capture shares the object — JLS 15.27.2 by-
  value capture of the reference; mixed I/J/D captures; per-iteration
  loop captures through an ArrayList),
  `LambdaThis` (implicit + explicit `this` capture — REF_invokeSpecial
  shape),
  `MethodRefStatic` (compiled + native static targets: `Math::abs`,
  `Integer::valueOf`, `Math::max` — exercises the unbox/box adaptation),
  `MethodRefBound` (bound native virtual, bound compiled virtual, bound
  collection receiver, receiver captured once — later reassignment
  invisible),
  `MethodRefUnbound` (receiver-as-first-SAM-arg: `String::toUpperCase`,
  `String::substring` with an unboxed int arg, `String::length`),
  `MethodRefCtor` (native `ArrayList::new`, compiled `Box::new` with an
  unboxed ctor argument, `Object::new`),
  `LambdaInCollections` (`forEach` with capture + block lambda, `removeIf`
  unboxing per element, empty-list edges),
  `LambdaGC` (20 000 closure churn with kept survivors + 100-closure
  accumulation — the gate-9 forced-GC rooting proof runs this fixture
  with a collection at every allocation).
- The `cfg_equiv` gate covers the new fixtures automatically (closure
  construction is straight-line; `--emit-cfg` equivalence held on first
  run).

**Test inventory at wave end (local, Temurin 21.0.13):** 60-fixture
differential suite green, lambda fixtures green, negative tests green.
Suite guard raised to `>= 60`.

## Wave 4 — synchronized monitors (T19–T20)

**Delivered.**

1. **Intrinsic monitors on the heap** (`heap.rs`): every arena `Entry`
   carries a re-entrancy counter (`monitor: u32`, 0 = unlocked).
   `monitor_enter` (re-entrant, overflow = internal error — unreachable
   given the frame ceiling), `monitor_exit` (unowned exit →
   `IllegalMonitorStateException` with HotSpot's `current thread not
   owner` message), and `monitor_release` (the FrameGuard `Drop` safety
   net: decrements without the ownership check, debug-asserted never to
   underflow). The IMSE is allocated *after* the heap borrow ends — the
   first test run caught `throw_new` re-entering the borrow.
2. **Frame-scoped release** (`frame.rs`): `FrameGuard` gains a monitor
   stack (capacity 8 inline — the 99 % case, no reallocation in steady
   state). `monitorenter` records after acquiring; `monitorexit` pops the
   most recent matching record; the `Drop` releases the remainder in LIFO
   order — the monitor analogue of the root-snapshot slot discipline.
   Normal returns (ACC_SYNCHRONIZED prologues), `Err` propagation and
   panic unwinds all release; javac's structured `monitorexit` paths pop
   their records first, so the `Drop` release is a safety net for
   exceptional exits that outrun them, never a double release.
3. **`monitorenter`/`monitorexit`** (`ir.rs` decode rejection lifted, new
   IR variants; verifier pops one reference; emission pops the ref — null
   → NPE — acquires/releases, and records/unrecords).
4. **`ACC_SYNCHRONIZED` methods** (the M1.6 loud error lifted *only* now
   that it is correct): `MethodPlan.is_sync` recorded at planning;
   instance methods acquire on the receiver in the prologue; static
   methods acquire on a **synthetic per-class monitor object** —
   allocated lazily by the generated statics module (`class_monitor`),
   permanent roots via `gc_scan_roots`, distinct per class (pinned by
   `SyncStatic`). The prologue releases through the FrameGuard `Drop` on
   every exit path.
5. **`Object.wait/notify/notifyAll`**: loud runtime
   `UnsupportedOperationException` with a named reason (the M3_PLAN §7.1
   threading boundary). Registered as natives so javac-compiled calls
   fail loudly at runtime, never silently — no differential fixture
   (Temurin implements them).

**Tests.**
- `heap.rs` unit tests (4 new): enter/exit re-entrancy counts; unowned
  exit → IMSE with class and message pinned; FrameGuard `Drop` releases a
  recorded acquisition; unrecord pops the most recent matching record and
  the `Drop` releases the rest.
- Five differential fixtures (suite 60 → 65, all three-channel green vs
  Temurin 21.0.13):
  `SyncMethod` (synchronized instance + static methods, self-reentrant
  call chains both instance and class-monitor),
  `SyncBlock` (`synchronized(this)` nested re-entrancy, two distinct
  object monitors in deterministic order, a static-field monitor),
  `SyncUnwind` (exception through a synchronized block → structured
  release → re-acquisition works; exception out of a synchronized
  method → frame-exit release → re-acquisition works),
  `SyncReentrant` (100-deep recursive re-entrancy × 50 + 100 000
  enter/exit pairs — the stress assertion),
  `SyncStatic` (class-monitor acquisition per call + two distinct
  per-class monitors across classes).

**Honesty notes.**
- The runtime is single-threaded (M3_PLAN §0 boundary): a monitor has no
  contention path; "ownership" is the re-entrancy count. Cross-thread
  semantics arrive with the threads milestone; nothing here claims them.
- `monitorexit` on an unowned monitor is not javac-reachable (javac
  always pairs enter/exit); the IMSE is pinned by unit test, not
  differential fixture.
- `wait/notify/notifyAll` are loud-unsupported at runtime by design.

**Test inventory at wave end (local, Temurin 21.0.13):** 65-fixture
differential suite green, monitor fixtures green, 4 new unit tests
green. Suite guard raised to `>= 65`.
