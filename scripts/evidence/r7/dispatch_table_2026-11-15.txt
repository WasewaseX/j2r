R7 — the dispatch-table selector match: MEASURED NO-GO (2026-11-15, run 3 of 5)

Question (Opt.md §3 R7): is the registry lookup — one string-tuple match
arm per user method, 2,169 arms in the jbox2d port — faster and cheaper to
compile as a match on a precomputed 64-bit selector?

Instruments (all committed or reproduced from the committed sources):
- rustc 1.99.1 (the pinned toolchain), this box, 2 vCPU.
- N = 2,169 synthetic entries (the jbox2d-port shape: 97 class names,
  distinct method names, four descriptors), generated by the scratch
  generator (source: scripts/evidence/r7/gen_main.rs — a scratch bin with
  a path dep on j2r-codegen, never shipped or vendored).
- OLD shape: the pre-R7 emission reproduced verbatim (bare
  `match (class, name, desc)` with one tuple arm per entry).
- NEW shape A: `(u64, class, name, desc)` 4-tuple match arms, sorted by
  selector (the first draft of the emitter).
- NEW shape B: `match j2r_disp_hash(class, name, desc)` with the full key
  verified INSIDE every arm (the final emitter shape; the selector-only
  match rustc can lower to an integer search).

Results — RUNTIME (release, one binary containing both lookups, 2,000
rounds x 2,169 hits + 2,169 misses per shape = 3.47 M calls per shape):

  old string-tuple match   94.2 / 96.5 ms   (~27 ns/call)
  new shape A (4-tuple)   750.3 ms          (~216 ns/call)
  new shape B (selector)  754.4 ms          (~216 ns/call)

Results — COMPILE (rustc -O --crate-type lib, incremental=none):

  old shape    3 s
  new shape   14-21 s (two runs; the selector tree + 2,169 inline
              key-verify bodies cost LLVM more than the string chain)

The verdict: NO-GO, and the premise itself does not reproduce on rustc
1.99. Opt.md §2.4 assumed the string-tuple match lowers to a *linear
chain* of string comparisons ("a linear string search executed 5.8 M
times"); the measured ~27 ns/call at N=2,169 proves rustc lowers it to a
BALANCED DECISION TREE instead (~11-12 cheap length/first-byte-rejecting
compares). Any selector-based scheme must first walk every key byte — a
serial FNV-1a multiply chain over ~30 bytes costs more than the whole
tree walk — and then still verifies the full key for exactness (the
dispatch must stay byte-faithful: a hash hit alone cannot select a
method, so the verify is load-bearing, not optional). The hash buys a
worse index than the one rustc already builds for free.

Landing (this commit): the machinery stays runnable behind
`Options::emit_hash_dispatch` / `--emit-hash-dispatch`, default OFF —
the M2-CFG precedent (prototype behind a flag, NO-GO for default
emission, re-evaluate when the premise changes). The new law tests pin
the selector algorithm (golden values), the separator law, the
ascending-selector byte-stable emission, the in-arm full-key verify, and
the order-independence. A future rustc whose string-match lowering
regresses to a linear chain can flip the flag and re-measure with the
same instruments.

DEFAULT-PATH PROOF (the flag changes nothing by default): the same 22
classes translated by the pre-R7 binary (worktree at the pre-R7 HEAD)
and by this binary (flag off) produce crates that are byte-identical —
`diff -r` clean over every emitted file and the manifest's SHA-256
input→emitted columns identical line-for-line (only the manifest's
mtime stamp differs).

FLAG-ON PROOF: the same fixture translated with --emit-hash-dispatch
builds and runs three-channel byte-identical vs Temurin 21.0.13+9
(stdout/stderr/exit, exit 0 == 0).

Wall-clock ledger (this box, foreground blocks): bench gen build 21.6 s;
old-shape -O compile 3 s; new-shape -O compiles 14 s and 21 s; bench
compile 18 s; bench run 0.9 s.
